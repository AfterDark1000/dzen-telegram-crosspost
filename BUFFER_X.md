## Публикация

Посты для X хранятся отдельно от Threads: `x_editorial_queue.json`. **Только записи со статусом `approved`** допускаются в Buffer; существующие материалы Дзен в X автоматически не переносятся, никакие тексты не обрезаются.

Редактор формирует самостоятельный текст X до 280 символов с коротким выразительным началом, фактической сутью и необязательным выводом. Не копировать 400-символьный текст Threads автоматически. После утверждения пользователем сохраняет:
```json
{
  "id": "story-unique-20261030",
  "dzen_title": "Точный заголовок материала из Дзена",
  "x_text": "Полный утверждённый текст до 280 символов.",
  "include_dzen_link": false,
  "status": "approved"
}
```
Нельзя создавать две записи для одного точного заголовка. Не публиковать без однозначного совпадения с вышедшей статьёй Дзена. Материалы старше 72 часов не отправляются. Публикация «Дневник канала» по URL `https://dzen.ru/a/auL2PIuIqglEYkgF` исключена общим фильтром.

**Изображения в X (с 30 октября):** чередуем подтверждённые публикации по порядку: **первая с исходной горизонтальной обложкой Дзена, вторая только текст, третья снова с обложкой**. Выбираем по числу уже принятых Buffer записей (`status=queued`), а не по номеру запуска или дате. Никакие отдельные 4:5-обложки и Telegram-канал Instagram не нужны. Используем `image` из публичной ленты Дзена через Buffer GraphQL `assets: [{image: {url: ...}}]`. При отсутствии публичной HTTPS-картинки *изображение не заменяется текстом*: пост остаётся `approved`, чередование не сбивается. При подтверждении Buffer сохраняем `with_image` в очереди. Сверяем фактические вложения в Buffer и при восстановлении после сбоя — несовпадающая картинка означает остановку, а не дублирование. **Публичный URL исходной обложки должен оставаться доступным к моменту отложенной публикации в Buffer**; если CDN Дзена меняет URL, это может потребовать отдельного стабильного хостинга. Самый первый реальный тест с картинкой проверяем в Buffer после добавления.

Каждый часовóй запуск GitHub может поставить в Buffer не более **одного** одобренного X-поста. Buffer сам публикует согласно расписанию аккаунта X, без отправки «сейчас». При восьми ожидающих в Buffer (из десяти разрешённых Free) автоматизация прекращает добавление. Старые посты из архива не ставятся.

Перед отправкой получаем все запланированные и отправленные X-публикации через Buffer API; если идентичный текст уже был создан после сбоя контрольного сохранения, не делаем дубль, а записываем его ID. В `x_editorial_queue.json` после подтверждения меняется статус на `queued` и добавляются `buffer_post_id`, `dzen_id` и `dzen_url`. Публикация `queued` означает, что Buffer принял пост в очередь, а не что X его уже разместил.

GitHub State Checkpoint сохраняет эту очередь атомарно с остальными состояниями, сохраняя правки редактора из параллельных сессий и не перезаписывая чужие изменения.

Документация API: https://developers.buffer.com/guides/posts-and-scheduling.html
