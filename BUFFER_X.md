## Публикация

Посты для X хранятся отдельно от Threads: `x_editorial_queue.json`. **Только записи со статусом `approved`** допускаются в Buffer; существующие материалы Дзен в X автоматически не переносятся, никакие тексты не обрезаются.

Редактор формирует самостоятельный текст X до 280 символов с коротким выразительным началом, фактической сутью и необязательным выводом. Не копировать 400-символьный текст Threads автоматически. После утверждения пользователем сохраняет:
```json
{
  "id": "story-unique-20261030",
  "dzen_title": "Точный заголовок материала из Дзена",
  "x_text": "Полный утверждённый текст до 280 символов.",
  "include_dzen_link": false,
  "status": "approved"
}
```
Нельзя создавать две записи для одного точного заголовка. Не публиковать без однозначного совпадения с вышедшей статьёй Дзена. Материалы старше 72 часов не отправляются. Публикация «Дневник канала» по URL `https://dzen.ru/a/auL2PIuIqglEYkgF` исключена общим фильтром.

**Изображения в X (с 30 октября):** чередуем подтверждённые публикации по порядку: **первая с исходной горизонтальной обложкой Дзена, вторая только текст, третья снова с обложкой**. Выбираем по числу уже принятых Buffer записей (`status=queued`), а не по номеру запуска или дате. Никакие отдельные 4:5-обложки и Telegram-канал Instagram не нужны. Используем `image` из публичной ленты Дзена через Buffer GraphQL `assets: [{image: {url: ...}}]`. При отсутствии публичной HTTPS-картинки *изображение не заменяется текстом*: пост остаётся `approved`, чередование не сбивается. При подтверждении Buffer сохраняем `with_image` в очереди. Сверяем фактические вложения в Buffer и при восстановлении после сбоя — несовпадающая картинка означает остановку, а не дублирование. **Публичный URL исходной обложки должен быть доступен при немедленной передаче в Buffer.** Если CDN Дзена меняет URL, это может потребовать стабильного хостинга.

С 2 ноября 2026 каждый часовой запуск GitHub может передать в Buffer не более **одного** одобренного X-поста с `mode: shareNow`, `schedulingType: automatic`. Buffer получает команду **опубликовать сразу**, без ожидания слота расписания. Это запрос на отправку, не доказательство доставки в X: окончательный статус проверяется в Buffer (`Sent`/`Error`) и профиле X. Если восемь записей находятся в состояниях `scheduled` или `sending`, новые запросы задерживаются в качестве защитной меры. По-прежнему не допускаются неутверждённые посты и статьи старше 72 часов; старый архив самопроизвольно не публикуется.

Перед отправкой получаем записи Buffer в статусах `scheduled`, `sending` и `sent`; если идентичный текст уже был принят после сбоя контрольного сохранения, не создаём дубль, а восстанавливаем его ID. В `x_editorial_queue.json` после подтверждения меняется статус на исторически сложившийся `queued` и добавляются `buffer_post_id`, `dzen_id` и `dzen_url`. **Статус `queued` теперь означает лишь подтверждённый приём Buffer команды `shareNow`, а не подтверждение фактической публикации в X.** Ошибки доставки нужно отслеживать в Buffer. Отдельное ручное `Publish Now` после `shareNow` не требуется.

GitHub State Checkpoint сохраняет эту очередь атомарно с остальными состояниями, сохраняя правки редактора из параллельных сессий и не перезаписывая чужие изменения.
